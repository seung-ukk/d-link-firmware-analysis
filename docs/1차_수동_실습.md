# 1차 중간보고서 수동 실습: ZIP에서 rootfs까지

이 문서는 1차 보고서에서 직접 실행한 순서를 팀원용으로 옮긴 것이다. **WSL Ubuntu의 저장소 루트**에서 실행한다. `python3 - <<'PY' ... PY` 전체는 터미널에 직접 입력하는 **한 개의 명령**이다. 각 소절의 명령 1~3개를 실행하고 실제 출력을 확인한 다음 다음 소절로 넘어간다.

분석 파일은 `analysis/original`과 `analysis/hotfix_b03`에 둔다. 1차 보고서의 `output/manual_first_report/...`와 경로만 다르며, 이렇게 해야 [2차 실습](../README.md#2-2차-보고서-docker-준비)이 동일 추출물을 사용할 수 있다. 기존 파일이 있으면 Python 코드가 덮어쓰지 않고 멈춘다.

## 0. 배포 ZIP의 목록·식별·압축 상태

먼저 [D-Link 공식 목록](https://support.dlink.com/resource/products/dir-882/REVA/)에서 받은 두 파일을 `firmware/original.zip`, `firmware/hotfix_b03.zip`으로 둔다.

```bash
unzip -l firmware/original.zip
unzip -l firmware/hotfix_b03.zip
sha256sum firmware/original.zip firmware/hotfix_b03.zip
```

각 ZIP에 BIN·PDF 두 파일이 보이는지 확인한다. ZIP SHA-256은 일반 `fe85902d34cbeae8340fb6f9bf05117d445bcedf3fc6b8b017c3bedf2baff86a`, Hotfix `79e8712201b40ea128b8e776d7d0c02c0ae25e58b60d0b02d3d928eaa2cea5d1`이다. 다르면 파일명·다운로드 완료·버전을 확인한다. **화면 1:** 두 ZIP 목록과 식별값.

```bash
unzip -t firmware/original.zip
unzip -t firmware/hotfix_b03.zip
mkdir -p analysis/original analysis/hotfix_b03
```

각 `unzip -t`의 `No errors detected`를 확인한다. 이 명령은 검사만 하며 파일을 추출하지 않는다. **화면 2:** 두 ZIP 압축 검사.

## 1. ZIP에서 BIN·PDF 추출

```bash
unzip -n firmware/original.zip -d analysis/original
unzip -n firmware/hotfix_b03.zip -d analysis/hotfix_b03
sha256sum analysis/original/DIR882A1_FW130B06.bin analysis/hotfix_b03/DIR882A1_FW1.30B06.bin
```

`-n`은 기존 파일을 덮어쓰지 않는다. BIN SHA-256은 일반 `573ab7ae729c44ef9c4aa52941f5b0ec1d44dd4c2d921cc461a6cb912c40e4d9`, Hotfix `d39ff294506b1f58592cfd30bbc4e690f43bc4d366dcaed5bf3be50a2dc21587`이다. **화면 3:** 추출과 BIN 식별.

```bash
file analysis/original/DIR882A1_FW130B06.bin analysis/hotfix_b03/DIR882A1_FW1.30B06.bin
xxd -l 32 analysis/original/DIR882A1_FW130B06.bin
xxd -l 32 analysis/hotfix_b03/DIR882A1_FW1.30B06.bin
```

`file`은 BIN을 `data`로 표시할 수 있다. `xxd`의 첫 4바이트 `53 48 52 53`은 `SHRS`다. **화면 4:** 암호화 BIN의 형식과 헤더.

## 2. SHRS 복호화: 원본

코드는 SHRS 헤더의 길이·IV와 암호문을 읽고, 세 SHA-512 내부 검사에 통과한 평문만 저장한다. 키·헤더 구조는 이 펌웨어에 대해 앞선 형식 조사에서 확인한 값을 사용한다. **이 내부 검사는 제조사 서명 검증이 아니다.**

```bash
python3 - <<'PY'
from pathlib import Path
import hashlib
import struct
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

src = Path("analysis/original/DIR882A1_FW130B06.bin")
dst = src.with_name("DIR882A1_FW130B06.decrypted.bin")
raw = src.read_bytes()
assert raw[:4] == b"SHRS", "SHRS header missing"
plain_len, cipher_len = struct.unpack(">II", raw[4:12])
encrypted = raw[1756:1756 + cipher_len]
assert len(encrypted) == cipher_len, "encrypted data truncated"
key = bytes.fromhex("c05fbf1936c99429ce2a0781f08d6ad8")
assert hashlib.sha512(encrypted).digest() == raw[156:220], "encrypted hash mismatch"
decryptor = Cipher(algorithms.AES(key), modes.CBC(raw[12:28])).decryptor()
plain = (decryptor.update(encrypted) + decryptor.finalize())[:plain_len]
assert hashlib.sha512(plain).digest() == raw[92:156], "plaintext hash mismatch"
assert hashlib.sha512(plain + key).digest() == raw[28:92], "keyed hash mismatch"
assert not dst.exists(), "output already exists; refusing to overwrite"
dst.write_bytes(plain)
print("SHRS checks: 3 passed")
print("plain bytes:", len(plain))
print("plain SHA-256:", hashlib.sha256(plain).hexdigest())
print("first 4 bytes:", plain[:4].hex())
print("saved:", dst)
PY
```

기존 실습에서는 `plain bytes: 13552522`, 첫 4바이트 `27051956`이 나왔다. 해시 불일치·길이 오류가 나면 입력 BIN과 SHRS 오프셋을 확인한다. **화면 5:** 원본 복호화와 세 검사.

`file`에서 MIPS용 uImage와 LZMA가 표시되는지, `0xa0`부터 LZMA 데이터가 시작되는지 확인한다. **화면 7:** 두 uImage 형식과 LZMA 시작점.

## 4. uImage의 LZMA 커널 해제: 원본

uImage의 크기 필드를 검사한 뒤 160바이트 헤더 다음 데이터를 해제한다.

```bash
python3 - <<'PY'
from pathlib import Path
import hashlib
import lzma
import struct

src = Path("analysis/original/DIR882A1_FW130B06.decrypted.bin")
dst = src.with_name("DIR882A1_FW130B06.decrypted.unpacked")
raw = src.read_bytes()
assert raw[:4] == bytes.fromhex("27051956"), "uImage header missing"
data_len = struct.unpack(">I", raw[12:16])[0]
assert len(raw) - 160 == data_len, "uImage data length mismatch"
kernel = lzma.decompress(raw[160:], format=lzma.FORMAT_ALONE)
assert not dst.exists(), "output already exists; refusing to overwrite"
dst.write_bytes(kernel)
print("compressed bytes:", data_len)
print("unpacked bytes:", len(kernel))
print("unpacked SHA-256:", hashlib.sha256(kernel).hexdigest())
print("saved:", dst)
PY
```

기존 실습은 압축 데이터 13,552,362바이트, 해제한 커널 19,102,144바이트였다. **화면 8:** 원본 uImage 길이 검사와 LZMA 해제.

## 6. 커널 내부 initramfs 찾기: 원본

해제한 커널 안에서 LZMA 시작 후보를 순회하고, 압축 해제 결과가 `070701`로 시작하는 CPIO인지 확인한다. 매직값이 나와야 initramfs 후보라고 판정한다.

```bash
python3 - <<'PY'
from pathlib import Path
import hashlib
import lzma
import re

src = Path("analysis/original/DIR882A1_FW130B06.decrypted.unpacked")
dst = src.parent / "initramfs.cpio"
kernel = src.read_bytes()
for match in re.finditer(b"\x5d\x00\x00", kernel):
    try:
        decoder = lzma.LZMADecompressor(format=lzma.FORMAT_ALONE)
        cpio = decoder.decompress(kernel[match.start():], max_length=100_000_000)
    except lzma.LZMAError:
        continue
    if cpio.startswith(b"070701") and decoder.eof:
        offset = match.start()
        break
else:
    raise ValueError("No LZMA-compressed CPIO found")
assert not dst.exists(), "output already exists; refusing to overwrite"
dst.write_bytes(cpio)
print("LZMA offset in unpacked kernel:", offset)
print("CPIO magic:", cpio[:6].decode())
print("CPIO bytes:", len(cpio))
print("CPIO SHA-256:", hashlib.sha256(cpio).hexdigest())
print("saved:", dst)
PY
```

기존 실습에서 LZMA 오프셋 8,951,772, CPIO 크기 46,324,736바이트였다. **화면 10:** 원본 initramfs의 위치·매직값.

## 8. CPIO에서 원본 rootfs 추출

newc CPIO 헤더와 각 항목의 길이·상대경로를 확인한다. 디렉터리와 일반 파일만 생성한다. 심볼릭 링크는 **대상 문자열을 목록에 기록**하되 링크를 만들지 않는다. 이 목록은 2차 실습에서 실행용 라이브러리 복사본을 준비할 때 필요하다.

```bash
python3 - <<'PY'
from pathlib import Path, PurePosixPath
from collections import Counter
import json
import stat

src = Path("analysis/original/initramfs.cpio")
out = src.parent / "rootfs"
inventory = src.parent / "rootfs_inventory.json"
data = src.read_bytes()
assert not out.exists() and not inventory.exists(), "output exists; refusing to overwrite"
out.mkdir()
pos = 0
counts = Counter()
records = []

while True:
    assert data[pos:pos + 6] in (b"070701", b"070702"), "invalid CPIO header"
    h = [int(data[pos + 6 + i * 8:pos + 14 + i * 8], 16) for i in range(13)]
    mode, size, namesize = h[1], h[6], h[11]
    name_bytes = data[pos + 110:pos + 110 + namesize]
    assert namesize > 0 and name_bytes.endswith(b"\0"), "invalid CPIO name"
    name = name_bytes[:-1].decode("utf-8")
    start = (pos + 110 + namesize + 3) & ~3
    content = data[start:start + size]
    assert len(content) == size, "truncated CPIO entry"
    pos = (start + size + 3) & ~3
    if name == "TRAILER!!!":
        break
    rel = PurePosixPath(name)
    assert rel.parts and not rel.is_absolute() and ".." not in rel.parts and "\\" not in name, "unsafe path"
    dest = out.joinpath(*rel.parts)
    item = {"path": name, "mode": oct(mode)}
    if stat.S_ISDIR(mode):
        dest.mkdir(parents=True, exist_ok=True)
        counts["directories"] += 1
    elif stat.S_ISREG(mode):
        dest.parent.mkdir(parents=True, exist_ok=True)
        dest.write_bytes(content)
        dest.chmod(mode & 0o777)
        counts["regular files"] += 1
    elif stat.S_ISLNK(mode):
        item["symlink_target"] = content.decode("utf-8")
        counts["symlinks listed, not created"] += 1
    else:
        counts["special entries listed, not created"] += 1
    records.append(item)

inventory.write_text(json.dumps(records, indent=2), encoding="utf-8")
print("entries:", len(records))
for kind, count in counts.items():
    print(kind + ":", count)
print("extracted to:", out)
print("link inventory:", inventory)
PY
```

기존 실습과 같이 `entries: 1693`, 디렉터리 144, 일반 파일 1,392, 링크 목록 157이 예상된다. **화면 12:** 원본 CPIO 집계와 추출 위치.

## 10. 파일시스템과 웹 구성 확인

```bash
find analysis/original/rootfs -maxdepth 2 -type d | sort
find analysis/hotfix_b03/rootfs -maxdepth 2 -type d | sort
file analysis/original/rootfs/bin/lighttpd analysis/hotfix_b03/rootfs/bin/lighttpd
```

`bin`, `lib`, `etc_ro`, `www` 등의 디렉터리와 두 `lighttpd`의 MIPS ELF 형식을 확인한다. **화면 14:** 두 rootfs 구조.

```bash
grep -nE 'server\.modules|mod_fastcgi|mod_cgi|server\.document-root|server\.port|fastcgi\.server|HNAP1|socket|bin-path|cgi\.assign' analysis/original/rootfs/etc_ro/lighttpd/lighttpd.conf
file analysis/original/rootfs/bin/prog.cgi analysis/hotfix_b03/rootfs/bin/prog.cgi
file analysis/original/rootfs/lib/librcm.so analysis/hotfix_b03/rootfs/lib/librcm.so
```

`/HNAP1/`의 FastCGI `bin-path`가 `/bin/prog.cgi`인지 본다. `prog.cgi`는 MIPS ELF 실행파일, `librcm.so`는 공유 라이브러리다. 이것은 **설정상의 연결**과 파일 형식 확인이지 웹 서버 기동 결과가 아니다. **화면 15:** 설정과 실행파일·라이브러리 형식.

```bash
readelf -d analysis/original/rootfs/bin/prog.cgi | grep -E 'NEEDED|RPATH|RUNPATH'
readelf -d analysis/hotfix_b03/rootfs/bin/prog.cgi | grep -E 'NEEDED|RPATH|RUNPATH'
command -v python3 unzip file xxd readelf docker
```

두 `prog.cgi`의 동적 의존성에 `libfcgi.so.0`, `librcm.so` 등이 보이는지 확인한다. `command -v`는 사용 도구의 설치 위치를 보여준다. **화면 16:** 두 실행파일의 의존성과 환경. 여기까지가 1차 보고서 범위다. 2차 실습은 [README의 Docker 준비](../README.md#2-2차-보고서-docker-준비)에서 계속한다.
